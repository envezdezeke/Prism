# Plan 02-04 (trimmed): Alerts feed and minimal inbox

## Goal
The rail gains Inbox (pending count) and Alerts. Alerts is built in full; the inbox is the smallest thing that lets the demo answer a request.

## Must haves
- Alerts feed: alerts with `at` at or before the clock time, newest first; columns Time, Level (Alert, Escalation, Second escalation by message prefix), Deal (navy link), Stage, To (role label, id in tooltip), Message; a 2px amber left edge and amber level text on escalations only. Empty and error states per 02-UI-SPEC.
- Inbox: Pending (oldest first) and Answered (newest answer first) lists at the clock time. Each item shows type label, deal link, sent time, recipient role, waiting time and the full message. Reply buttons are exactly the item's `options` (first navy, rest outline). `decline` and `release_hold` confirm inline first.
- `POST /api/inbox/{id}/reply` body is exactly `{option}` (plus `note` only if typed). 409 and 422 messages per spec; network failure shows describeError.
- Session answers live in an in-memory zustand overlay applied from `answered_at` (pure `inboxWithOverlayAt` in `timeview.ts`, tested); scrubbing back shows the item pending again and it cannot be sent twice.
- Rail: Pipeline, Inbox with the pending count, Alerts (plus Fraud graph from 02-05).

## Out of scope (cut by D-32)
Inbox two-pane layout with segmented control, optional note input, and the detail page's human-request overlay join.

## Verify
`npm --prefix ui run test`, `lint`, `audit`, `build`; manual: answer `inbox-001` with Approve, rail count drops.
